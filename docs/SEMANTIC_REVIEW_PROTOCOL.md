# FactDeck 语义复核协议

语义复核不等于文字引用检查，也不以箭头作为逻辑关系的唯一形式。执行端必须结合来源文本、表格、图示和页面结构检查内容与关系是否成立。

## 复核输入

- 首次检查提供当前版本的全部页面、事实引用、摘要要点、章节大纲和遗漏说明。修订复核只提供影响范围的详细证据，其余页面提供存档结论与编号。
- 每页所引用的来源原文；涉及图表时，提供原件整页或足以核对关系的完整截图。
- 上一轮未闭环问题及其处置状态，以及直接受影响的页面；不能漏掉问题依赖的前后文。已关闭问题保留本地账本，不重复传送全部原文。
- 任务合同记录的版本号和输入校验值；审核结果必须绑定同一版本。

## 逐页检查

1. **事实与限定**：数字、单位、比较符号、否定、对象、时间、人群和适用范围是否与原文一致；摘要是否丢失关键限制。
2. **上下文**：转折、代词、结论前提和证据限制是否保留；单句是否因省略前后文而改变含义。
3. **关系类型**：核对条件、因果/相关、先后、并列、包含、分组、比较、阈值归属及跨页承接。不得把“列出”改成“同时满足”或“任选其一”，除非原文明确支持。
4. **关系方向**：原文用箭头时核对起点、终点和标签；原文用文字或表格时核对条件与结果、行列对应及阅读顺序。没有箭头不代表没有关系，也不能据页面布局自行补关系。
5. **完整性**：将每个摘要要点、章节要点和需要教学的来源图表逐项映射到页面；缺失项必须记录为明确遗漏或人工待确认，不能默认为已覆盖。
6. **页面表达**：页面顺序、分组、标题和视觉层级不能制造原文没有的关系；检查同页/跨页重复、上下文断裂和密集内容的可读性。

## 整套回归与问题闭环

- 对全部页面运行代码确定性检查：事实引用、逐字来源、对象可解析、结构和章节覆盖。代码通过不等于语义通过。
- 独立执行端必须与页面作者身份不同；首次检查全部页面及摘要/章节映射，修订检查计算出的影响范围。每条问题都记录级别、页面、来源位置、证据、错误/缺失的关系及建议处置。
- 每轮复核都要回看上一轮问题：标记为已修复（给出新页面证据）、待人工确认、依据不足而保留，或仍未解决。未闭环的阻断不得被总通过状态覆盖。
- 对新发现的问题，判断它是内容错误、来源证据缺失、页面表达歧义还是人工决策，不把它们混为一类。
- 复核结果只能说明证据和问题状态，不能替用户确认医学内容，也不能启动正式 PPT 生成。

## 覆盖证明与停止条件

多轮模型复核不能证明“绝无遗漏”。如果每轮只提交页面并让审核者自由通读，审核者会重复关注显眼内容，却可能持续漏掉相同类型的限定、图表单元或跨页关系。因此，“又做了一轮且没发现问题”不能单独作为通过证据。

每次整套审核必须同时维护以下可检查的覆盖账本，并绑定输入版本及 SHA-256：

1. **来源清单**：列出所有来源文件、页数、每页的文字/表格/图/脚注/图注区域。不可读、重复、空白或未纳入教学的区域也要有状态和理由。
2. **来源到教学内容映射**：每个大纲要点及需讲授的来源单元都对应页面 ID；状态只能是已呈现、明确不纳入并说明理由、待人工确认。不能只用“整章已覆盖”代替逐项映射。
3. **关系账本**：对每个关键条件、结果、比较、顺序、并列/择一、包含、阈值归属和跨页承接，记录来源证据、页面表达方式及方向；原文未明确的关系标为未知，禁止自动补全。
4. **问题账本**：每项历史或新问题有稳定 ID、严重度、来源和页面证据、影响范围、处置状态、修订版本及复核证据。关闭问题必须由证据支持，不能仅填写“已修复”。

审核拆成两个有不同检查目标的独立检查表：

- **覆盖/逐字检查**：从来源页逐项向页面核对数字、单位、否定、限定、脚注、表格行列和未纳入项；不从页面反向猜来源内容。
- **语义/关系检查**：从大纲要点和来源关系向页面核对上下文、逻辑类型、方向、分组和视觉表达；不能把“列表”自行解释为合取或择一。

两表由独立执行端完成，均须直接查看必要的来源页面图像。代码检查用于验证清单完整性、引用和映射，不代替这两类判断。结果必须列出实际覆盖数量（来源页、来源单元、大纲要点、页面、历史问题）及未能检查的范围，不能只给“通过”。

**允许进入人工内容确认的条件**：所有来源和大纲范围都有状态；所有阻断均已修复并经独立复核，或明确列为需要用户裁定的项目；不再存在未分配、无证据关闭或无法追溯的问题。非阻断备注须逐项解决，或说明影响并提交用户决定。任何待人工裁定项都必须在确认页显著列出，不能被“审核通过”掩盖。

修订后采用按影响范围的回归：复核修改页、直接依赖同一事实/关系的页面，以及对应的来源映射；然后重跑账本完整性和代码校验。只有来源范围、事实库或全局结构变化时才重做全量语义检查。每轮都保留此前账本，不能用新结果覆盖旧问题历史。

通过上述条件，最多能说明“在列明的来源范围、版本和检查方法下，未发现未处理阻断”；不能保证绝无遗漏，也不等于医学专家认可。人工确认后若内容或来源变化，必须产生新版本并重新检查受影响范围。

## 代码实施（2026-10-10）

| 协议要求 | 实现 |
|---|---|
| 问题账本：稳定ID、严重度、证据、处置状态、历史 | `w.issue_ledger`（`app/review_ledger.py`），总结用 SR-、语义用 SEM-；状态 OPEN / NEEDS_HUMAN / RETAINED / FIXED / HUMAN_RULED，逐轮历史不覆盖 |
| 每轮回看上一轮问题，关闭须有证据 | 合同 `prior_issues` 须逐条处置；FIXED 须带 `evidence_refs`（当前版本编号）；与本轮判定矛盾的处置被拒绝；同一位置的问题并入原编号；复发用 `reopens` |
| 区分内容错误、证据缺失、表达歧义、人工决策 | 新问题必填 `category`；HUMAN_DECISION 和关系 UNKNOWN、覆盖 NEEDS_HUMAN 直接进入待人工裁定 |
| 两张独立检查表 | SEMANTIC_REVIEW 的 `COVERAGE` 与 `RELATIONS` 两个任务；须由不同且非作者的执行端完成，不合格身份领不到任务 |
| 来源清单、来源到教学内容映射 | COVERAGE 合同的 `source_pages`（区域统计、呈现页）与 `teaching_items`（提纲条目/要点、章节、关键要点）；每项须有状态与理由 |
| 关系账本 | RELATIONS 合同的 `relations`：总结关系、箭头、每个多条目页面的分组结构；SUPPORTED / UNSUPPORTED / UNKNOWN |
| 直接查看来源页面图像 | 每页附 `image_url`；`must_view_source_pages` 须出现在 `viewed_source_pages` |
| 列出实际覆盖数量和未检查范围 | 检查记录 `counts` 与 `unchecked`，工作台显示 |
| 按影响范围回归 | `regression`：FULL（首次或事实库/总结/来源变化）或 IMPACT（改动页、共用事实/关系页、相邻页、有未闭环问题的页须复读，其余可 CARRIED） |
| 待裁定项须显著列出 | 工作台与确认稿置顶；内容确认须提交 `acknowledged_issues` 以确认已知悉未闭环提示；阻断（含待裁定）仍阻止确认与生成 |
| 作者逐条处理 | DECK 合同 `review_issues`，修订版须提交 `issue_responses`（CHANGED / NOT_CHANGED / NEEDS_HUMAN）；是否修复仍由独立复核判定 |

代码检查只证明账本完整、引用可解析、处置与判定一致，不判断语义是否正确。

### 历史证据复用（2026-10-11）

`semantic_review.checkpoint` 对真实存档报告运行同一验收器，在副本中验证输入版本、独立作者、页面结论、来源查看记录和问题处置，并绑定原任务及结果校验值。
记录保存到 `semantic_review_baselines`，不会写入当前通过状态、关闭现场问题或授予人工确认。
取消的任务可以保留已实际完成的检查证据；取消本身不是审核通过。

后续 `regression` 可从存档基线计算 IMPACT。报告中的问题页面仍必须复读；补充发现须保留证据并加入复读范围。
来源、总结或事实库变化仍触发 FULL；协议字段升级不自动构成来源变化。
IMPACT 合同只给受影响页面的详细事实、相关总结章节和来源资料，其余来源页标 `read=false` 并附原分类理由。来源清单仍由代码完整维护，不声称执行端本轮重新阅读了这些页。

确认页将未闭环问题分成“需要你裁定的事项”和“由执行端修订与复核”，历史已处理记录单独显示；来源更正保留原文与原图入口。
网页不会自动启动云端执行端；排队、保存答复和确认内容分别记录，不能将排队解释成已运行。
